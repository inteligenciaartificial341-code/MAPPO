## MAPPO (Elite Ar)

Sistema de gestão de campo (ordens de serviço, obras VRF, GPS, check-ins), em transição de single-tenant (Elite Ar) para produto multi-tenant. As 17 stories de `_bmad-output/specs/spec-mappo/stories.yaml` (todo o épico) estão implementadas e publicadas — autenticação real, onboarding por Ramo, compressão de foto, GPS com consentimento, link público com expiração/XSS, verificação de sincronização, PWA, aba financeira, VRF restrito ao Ramo, mapa com avatar/histórico, convite de prestador gerado pelo gestor, pontos de entrada (WhatsApp/Compartilhar), multi-obra no VRF, avaliação do app, vocabulário de serviço genérico por Ramo + Ramo customizado, registro fotográfico genérico (Antes/Depois), minitutorial guiado (coach-marks). App em `index.html` (HTML+CSS+JS, sem build, sem framework) sincronizado com Cloud Firestore (SDK compat v10.12.2); `manifest.json`/`sw.js` (Story 7) e `avatar-1.svg` a `avatar-6.svg` (Story 10, avatares do mapa) são os únicos outros arquivos-fonte da aplicação. Auditoria técnica original em `_audit/mappo-initial-audit.md` (pré-Story-1; vários achados já corrigidos, ver `deferred-work.md` para o que continua real). Auditoria de segurança/código completa em 2026-09-01 (firestore.rules + index.html inteiro) achou gaps reais ainda não corrigidos — ver Known pitfalls e `deferred-work.md`.

## Policy

- `index.html` é o app inteiro em arquivo único — edite cirurgicamente (trecho/função específica); nunca reescreva ou reformate o arquivo inteiro, nem faça refactors amplos numa mesma tarefa.
- Uso de skills BMAD limitado a 4–5 por tarefa; se precisar de mais, quebre a tarefa em etapas menores com checagem ao final de cada uma.
- Ao final de cada etapa, pare e reporte um resumo do que foi feito seguido de uma pergunta direta pedindo autorização explícita antes de seguir pra próxima — nunca encadear etapas sem essa checagem. Não há um vocabulário fixo de status (`APROVADA`/`BLOQUEADA`) exigido; o que importa é a autorização explícita ter acontecido antes de avançar.
- Nunca executar deploy, alteração de `firestore.rules` em produção, ou migração de dados sem autorização explícita por escrito do proprietário — inclusive quando rodando em modo mais autônomo ("bmad loop"), esse gate nunca é afrouxado.
- Antes de qualquer migração de dados, exigir backup do Firestore/`localStorage` e um plano de rollback definido — nunca migrar "às cegas". Uma migração não-destrutiva (nunca apaga/sobrescreve a chave/dado original) é o padrão preferido — dobra como o próprio plano de rollback (reverter o commit basta).
- Commitar em `main` é o caminho normal deste projeto (um proprietário, um ramo), **mas sempre com autorização explícita do proprietário para o commit específico** — é essa autorização por commit que substitui o fluxo de branch. Ramo separado só quando ele pedir. A regra anterior, que dizia proibir commit direto em `main`, foi corrigida em 25/09/2026 no `CLAUDE.md` por proibir exatamente o que todo commit do histórico faz.
- **A autorização de um commit inclui publicá-lo** (decidido pelo proprietário em 08/10/2026): um "pode" vale para commitar e empurrar na mesma ida. O que entra continua sendo mostrado por caminho explícito antes, e `npm test` continua tendo de estar verde. **Exceção:** quando a entrega depende de algo que só o proprietário faz antes — hoje, publicar `firestore.rules` no Console —, não empurrar junto, porque o recurso nasceria morto.
- Nenhuma mudança em `firestore.rules`/`firestore.indexes.json` vai a produção sem teste prévio no Firebase Emulator Suite (`@firebase/rules-unit-testing`; a suíte vive em `testes/teste-regras.js`, no projeto `demo-mappo-regras` — o prefixo `demo-` garante que nenhuma verificação alcança produção. Regra alterada sem caso novo correspondente reprova).
- Toda alteração em `index.html` ou nos ícones da casca (`SHELL_URLS` do `sw.js`) exige trocar o `CACHE_VERSION` do `sw.js` — é a impressão digital da casca, e sem ela o navegador não instala o Service Worker novo, então ninguém é avisado da versão nova. `npm test` reprova e entrega a linha pronta para colar (`0016f50`, 01/10/2026). Mesma classe da regra acima: mecanismo, não memória — depender de lembrar falhou em 41 publicações seguidas.
- Testar fluxos reais (cadastro, GPS, etc.) contra produção sempre com dados descartáveis e identificáveis como teste (nome/e-mail únicos) — não há emulador para o app em si, só para `firestore.rules`; limpar workspaces/contas de teste depois.

## Running and verifying

- `npm test` roda a suíte inteira em série e sai com código diferente de zero se alguma falhar; `npm run test:lista` é a fonte viva de quantas são e de como estão classificadas. Nenhuma entrega é dada por pronta com ele vermelho. **Atenção: isso AVISA, não impede** — o CI roda depois do commit já estar em `main` e o GitHub Pages publica sem consultá-lo; só proteção de ramo impediria, e ela segue desligada (ver `CLAUDE.md`, "O que o CI NÃO garante").
- Para abrir o app à mão, qualquer servidor estático na raiz do repo serve. As suítes não dependem disso: cada uma sobe o próprio servidor em porta aleatória.
- Emulator Suite exige Java no PATH desta sessão (não persiste entre chamadas): `export PATH="/c/Program Files/Eclipse Adoptium/jdk-21.0.12.101-hotspot/bin:$PATH"` antes de `firebase emulators:start`.
- `firebase.json` cobre `firestore` (regras/índices) e `emulators`; não há bloco `hosting` — `firebase deploy` hoje não publica o site (isso vai via `git push` para `main`, servido por GitHub Pages).

## Known pitfalls

- Todo workspace novo nasce `status:'pendente'` em `firestore.rules` — sem dado acessível até o dono do projeto aprovar manualmente no Firebase Console (editar o campo pra `'ativo'`, fora do alcance das regras). Esquecer esse passo depois de um cadastro parece bug ("não consigo ver meus dados"), mas é o gate funcionando como desenhado — não "corrigir" removendo o gate sem decisão explícita do proprietário.
- Vínculo de técnico ao workspace: desde a Story 11, o caminho principal é o gestor gerar um código de convite de uso único (`convites/{codigo}`, revogável) que o próprio prestador consome (nome + código, sem o gestor colar nada). O fluxo antigo (colar UID copiado manualmente, sem verificação de identidade) continua existindo só como fallback "Avançado", e carrega o mesmo risco residual de sempre se usado — mas deixou de ser o caminho principal.
- Vocabulário de OS/técnico (dropdown "Tipo de Serviço", "Quantidade de splits", módulos ❄️Split/🌡️VRF) continua fixo em refrigeração pra qualquer Ramo — só o checklist é personalizado por Ramo (Story 2). Não é bug, é escopo intencionalmente menor (Addendum B, registrado em `deferred-work.md`) até uma conversa de desenho dedicada.
- `firestore.rules` (`workspaces/{wsId}/data/{docId}`, `isGestorOnlyDoc()`) trava escrita a gestor pra 10 docIds (config, cliente, manutenção, financeiro, vocabulário, obras VRF) desde a correção de 2026-09-01 — antes só `mappo_tecnicos` era travado. `mappo_os` continua escrevível por qualquer membro de propósito: técnico precisa dela pra check-in/checklist/foto, e o blob JSON único (AD-8) não permite validar campo a campo na regra — significa que um técnico ainda pode adulterar `valor`/`valorStatus`/`tecnico` de QUALQUER OS via SDK direto, não só a própria. Esse resíduo é estrutural, não um detalhe esquecido — ver `deferred-work.md` antes de tentar "só adicionar uma checagem".
- `wsId` = `_slugify(empresa)` + sufixo aleatório de 5 chars (`_gerarSufixoWs`, desde a correção de 2026-09-01) — nunca mais só o nome da empresa, então não dá mais pra "sequestrar" o slug de uma empresa-alvo só sabendo o nome dela. `workspaces/{wsId}` ganhou `criadoPor:uid` (rastreabilidade, não checado em regra). `wsId` nunca é exibido em nenhuma tela — é só chave interna de path/coleção.
- Apesar do padrão único de escape já estabelecido (AD-12), nada garante estruturalmente que toda interpolação de dado de usuário em `innerHTML` passe por `escapeHtml` — auditoria de 2026-09-01 achou 14 pontos reais sem escape (corrigidos no mesmo dia). O CI existe, mas **nenhuma suíte cobre escape de HTML**: uma regressão aqui passa verde — ao tocar qualquer trecho que gera HTML via template string com dado dinâmico, confirme escape de verdade, não assuma que "o padrão já cobre".
- **Existe suíte anti-regressão commitada desde 25/09/2026** (`56db2a0`): scripts Node auto-contidos com Playwright em `testes/`, rodados por `npm test` e pelo GitHub Actions a cada push em `main` e a cada PR. Veja `testes/README.md` antes de escrever teste novo — e `npm run test:lista` para o número e a classificação atuais, que é a fonte viva. Antes disso os testes eram scripts efêmeros descartados ao final; para mudança de regra do Firestore o padrão segue sendo o Emulator Suite — e desde `9d99f3c` ele **está** no `npm test` e no CI, em `testes/teste-regras.js` (`npm run test:regras`), no projeto `demo-mappo-regras`, que nunca toca produção.
- Sistema VRF: `vrfObra` (objeto único) virou `vrfObras` (lista, Story 13) — um workspace pode ter várias obras, cada uma com progresso/fotos/notas/check-ins/relatórios isolados; técnico só vê as obras que o gestor atribuiu a ele. A chave antiga (`mappo_vrf_obra`, singular) continua em `SYNC_KEYS` de propósito — nunca é apagada, é o próprio plano de rollback da migração.
